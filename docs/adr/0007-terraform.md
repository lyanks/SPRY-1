# 0007 - Terraform for the infrastructure, applied by HCP Terraform

Status: accepted (Lab 7)

## Context

Labs 4-6 added three CloudFormation templates (`auth.yaml`, `reports.yaml`, `ai.yml`) next to the
course template's four. They work, but:

- Each had its own deploy script with its own parameter plumbing (`scripts/auth.sh`, `reports.sh`, `ai.sh`).
- The project already reaches outside AWS (the Google OAuth client, GitHub) and needs a second
  environment, which one AWS-only tool describes badly.
- A change was visible only as a diff of YAML; the effect on the cloud (what is replaced, what is
  deleted) was visible only after it happened. In this project a stack delete once removed a
  database that could not be recreated.
- Lab 5 needed a constructed bucket name to escape a circular dependency, which hides the real
  relationship between the bucket, the permission and the notification.

## Decision

The three templates became Terraform in `infra/` (`auth.tf`, `reports.tf`, `ai.tf`). One root
module, one HCP Terraform workspace (`spry-dev`) in Remote execution mode, with the `env`-style
differences kept in variables so a second workspace is one more `.tfvars` file.

The existing resources were **adopted, not re-created**: the old stacks were redeployed with
`DeletionPolicy: Retain`, deleted (the resources stayed), and `import` blocks (generated by
`scripts/tf-imports.sh`) attached each real resource to its Terraform address. The migration was done
when `terraform plan` said `No changes`. `prevent_destroy` guards the user pool (every account that
signed up) and the reports bucket (every report).

The course template's stacks (backend, frontend, GitHub OIDC) stay CloudFormation: they are not part of
this lab, and `terraform output` and variables reach across the boundary.

## Alternatives

- **Stay on CloudFormation.** Free, AWS keeps the state, rollback is automatic. Rejected: AWS only, plan
  is an optional step, and a second environment or a second provider means a second tool.
- **CDK.** Real programming languages, but it generates CloudFormation and keeps its limits and its
  failure modes; one more build step for a small project.
- **OpenTofu.** Accepts the same files, and has an open licence (Terraform is BSL since 2023). Not
  chosen because the course and HCP Terraform use Terraform; the files would move unchanged.
- **Terraform from a laptop with state in S3.** Works, but then credentials live on laptops and the
  state bucket and lock table are another thing to bootstrap and protect.

## Consequences

- **Who can change the infrastructure, and how.** A pull request that changes `infra/*.tf`. HCP Terraform
  runs a speculative plan on it (shown as a check) and applies on merge to the default branch. Nobody
  runs `terraform apply` locally; the Makefile has no apply target. The account-wide change is visible in
  the plan before it happens, and the history is in Git.
- **Secrets.** The Google client secret is a sensitive workspace variable, never in a file or in
  Git. It does end up **in the state** (the identity provider's `provider_details`), and so does the
  database password the report builder's configuration reads from Secrets Manager. `sensitive` only hides
  values in plan output. So the state is as secret as the secrets: it is in HCP Terraform with
  access limited to the organization's members, never in Git, never on a laptop. The Lambda's
  environment variable `DB_PASSWORD` is visible in the function's configuration, as it was
  with CloudFormation (the function sits in a VPC without NAT and cannot call Secrets Manager).
- **If HCP Terraform is down.** The running system is not affected: the resources exist and work
  without Terraform. Only changes wait. For an emergency, the workspace can be switched to Local
  execution and a person with AWS credentials can run plan and apply with the state still stored (and
  locked) in HCP; if HCP itself is unreachable, state can be pulled from its last version. The lost
  piece would be the state, which is why it must not live only on one machine.
- **Credentials.** HCP Terraform needs permission to change AWS. The preferred way is dynamic credentials
  (OIDC, short-lived); where the organization forbids creating the identity provider, the fallback is a
  narrowly scoped IAM user's key stored as a sensitive workspace variable, which is a standing secret and
  must be rotated.
- **No automatic rollback.** A failed run stops halfway; the fix is a new commit and another run.
- **Drift.** A hand-made console change shows in the next plan and is reverted by the next apply. The fix
  for a real 23:00 emergency is to make it in the console, then write the same change in `infra/*.tf` the
  next morning, in a pull request, before the next apply.
- **Cost of the choice.** The state is ours to protect (HCP Terraform keeps every version of it), and new
  AWS features reach the provider days after they reach CloudFormation.
